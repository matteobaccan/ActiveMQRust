# message-identity Specification

## Purpose
Defines the OpenWire message and broker ID structures, preservation of client message IDs, broker sequence IDs, their ActiveMQ-compatible text form and duplicate detection.
## Requirements
### Requirement: OpenWire ID structures
The broker SHALL encode and decode the ActiveMQ ID types with the same OpenWire data types and fields as ActiveMQ, so they cannot be told apart from those of an ActiveMQ broker:

| Object | Type | Fields | Text example |
|---|---|---|---|
| ConnectionId | 120 | `value: String` | `ID:host-51234-1759672800000-1:1` |
| SessionId | 121 | `connectionId: String`, `value: i64` | `ID:host-51234-1759672800000-1:1:1` |
| ProducerId | 123 | `connectionId: String`, `sessionId: i64`, `value: i64` | `ID:host-51234-1759672800000-1:1:1:1` |
| ConsumerId | 122 | `connectionId: String`, `sessionId: i64`, `value: i64` | `ID:host-51234-1759672800000-1:1:1:1` |
| MessageId | 110 | `producerId: ProducerId`, `producerSequenceId: i64`, `brokerSequenceId: i64`; from version 10 also `textView: String` | `ID:host-51234-1759672800000-1:1:1:1:42` |
| BrokerId | 124 | `value: String` | `ID:host-61616-1759672800000-0:1` |

The `textView` field of `MessageId` SHALL be read and written only when the negotiated version is 10 or higher.

#### Scenario: MessageId round trip at version 12
- **WHEN** a `MessageId` with a `textView` is decoded and re-encoded at version 12
- **THEN** the produced bytes are identical to the input

#### Scenario: MessageId at version 9
- **WHEN** a message received at version 12 is dispatched to a consumer at version 9
- **THEN** the `MessageId` is encoded without `textView`, and the consumer's `JMSMessageID` equals the producer's

### Requirement: Client message ID preserved
The `MessageId` is generated by the client. The broker SHALL keep it intact, with the same fields and the same text representation, so that `JMSMessageID` is identical on the producer side and on the consumer side, and has the form `ID:<host>-<port>-<timestamp>-<n>:<n>:<n>:<n>:<n>`.

#### Scenario: Same JMSMessageID end to end
- **WHEN** a Java producer sends a message and records its `JMSMessageID`, and a consumer receives it
- **THEN** the consumer's `getJMSMessageID()` returns exactly the recorded string

### Requirement: Broker sequence ID
The broker SHALL set only the `brokerSequenceId` of each incoming `MessageId`, taking it from a single broker-wide monotonic counter, as ActiveMQ does. No other field of the `MessageId` SHALL be changed.

#### Scenario: Increasing broker sequence IDs
- **WHEN** three messages are sent, to two different queues, one after the other
- **THEN** their `brokerSequenceId` values are strictly increasing in arrival order

### Requirement: Text representation
The text form of a `MessageId` used in logs and in the admin console SHALL be the same as ActiveMQ's `MessageId.toString()`: the `textView` when present, otherwise `<connectionId>:<sessionId>:<producerId>:<producerSequenceId>`, where the first three parts are the text form of the `ProducerId`.

#### Scenario: Text form without textView
- **WHEN** a `MessageId` with `ProducerId` `ID:host-51234-1759672800000-1:1:1:1` and `producerSequenceId` 42 and no `textView` is formatted
- **THEN** the result is `ID:host-51234-1759672800000-1:1:1:1:42`

### Requirement: Broker-generated IDs
IDs generated by the broker, such as `BrokerId` and any message or object created by the broker, SHALL follow the ActiveMQ format `ID:<hostname>-<port>-<timestamp ms>-<counter>:<n>`, produced by a generator equivalent to ActiveMQ's `IdGenerator`: a seed made of host name, port and start time, a counter incremented per generated seed, and a per-ID sequence.

#### Scenario: BrokerId format
- **WHEN** a Java client reads the `BrokerId` from `BrokerInfo`
- **THEN** it matches `ID:<hostname>-<port>-<timestamp>-<n>:<n>`

#### Scenario: Unique IDs
- **WHEN** the generator produces 1,000,000 IDs
- **THEN** all of them are distinct

### Requirement: Duplicate detection
For each destination, the broker SHALL remember the last 1024 `producerSequenceId` values received from each producer. A message whose `ProducerId` and `producerSequenceId` are already in that window, for example a message resent after a client failover, SHALL be discarded without being stored, and SHALL still receive a `Response` if it was sent synchronously, as ActiveMQ's `producerAudit` does. The discard SHALL be logged at debug level. The window state of a producer SHALL be released when the producer's connection closes.

#### Scenario: Resent message discarded
- **WHEN** a producer sends a message and then sends the same `MessageId` again synchronously to the same queue
- **THEN** the second send receives a `Response`, and the queue holds only one copy

#### Scenario: Different producer sequence accepted
- **WHEN** a producer sends `producerSequenceId` 1, 2 and 3
- **THEN** all three messages are stored
