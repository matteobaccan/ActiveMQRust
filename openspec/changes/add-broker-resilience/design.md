## Context

Release builds use `panic = "abort"`; the per-connection task model means most failures can be confined to one connection if they are returned as errors instead of panics.

## Goals / Non-Goals

**Goals:** no input from a client can stop the broker; memory stays bounded by default; the service comes back by itself after a failure.
**Non-Goals:** persistence of in-flight messages across a restart (the broker stays in-memory by design).

## Decisions

- **Three fuzz targets, chosen by what a client can reach**: `decode_frame` (the command decoder, the only part of the broker reachable before the login), `primitive_map` (the marshalled properties of a message, decoded when a selector asks for one) and `selector` (text the client writes). *Alternatives considered*: one target driving a whole connection, which would spend its runs in the socket and the handshake rather than in the parser; no target for `primitive_map`, which nests by construction and so is exactly where nesting limits are worth testing.
- **cargo-fuzz in a package of its own, replayed by the suite on stable**: `fuzz/` is outside the broker's build because libFuzzer and nightly are not available on the Windows release toolchain, and `tests/fuzz_seeds.rs` replays the committed seeds and sweeps seeded random and mutated input, so the same entry points are guarded on every platform CI builds. *Alternatives considered*: a nightly fuzzing job in `build.yml`, which would fuzz for seconds per run and only on the platform that matters least; `cargo-afl`, with the same nightly requirement and without the corpus tooling.
- **Nesting is bounded, not caught**: `panic = "abort"` means a stack overflow cannot be caught, so the decoder counts how deep it is and refuses a frame past 32 levels, the limit nested primitive maps already used. *Alternatives considered*: `panic = "unwind"` with `catch_unwind` around each connection task, which trades the release profile for the chance of carrying on from a corrupted state; a larger thread stack, which moves the threshold without removing it.
- **A default memory limit of half the RAM, capped at 2 GB and floored at 256 MB**: with no `broker.max_memory_mb` the broker limits the memory its messages may hold to `min(2048, physical_mb / 2)` MB, never below 256. `max_memory_mb = <n>` still names the limit exactly and `0` still means no limit, which is what the key meant before and stays the documented way back to the old behaviour. The number is logged at startup with where it came from, because a limit nobody asked for must be visible. *Alternatives considered*: a plain 2 GB with no reading of the machine, which needs no platform code but hands a 1 GB virtual machine a limit that never bites, so the operating system kills the process before the broker refuses a message; a percentage with no cap, which lets a 256 GB server devote 128 GB of messages to a broker that is meant to be small; a percentage key of its own (`max_memory_percent`), three knobs where one absolute number already covers every operator who cares. When the machine's memory cannot be read the broker uses 2048 and says so, rather than falling back to the floor and refusing messages on a large machine for a reason nobody can see.
- **No `min_memory_mb`, and no preallocation**: the accounting is a counter (`broker::entry::Memory` adds a message's size while any copy is held and subtracts it when the last one drops), not an arena the broker owns, and there is no garbage collector whose growth a reserve would smooth. The JVM's `-Xms` exists because the JVM owns one contiguous heap whose resize is expensive and visible to the collector; here each body is its own allocation and mimalloc already takes memory from the system in large segments. What a reserve can still buy, fewer page faults on the first fill, needs no key: mimalloc reads `MIMALLOC_RESERVE_OS_MEMORY`, which `scripts/soak-compare.ps1` already sets behind `-PreallocateMemory`, and the one measurement there says it is not where the time goes (4 GB reserved with `max_memory_mb = 4096`: 1,383,663 of 1,383,663 messages at 337 MB/s, peak 1.0 GB, so the reserve was four times what the broker touched). *Alternatives considered*: a `min_memory_mb` that reserves at startup, which would be a performance knob dressed as a safety one; committing that memory so the broker fails fast when the machine cannot provide it, which trades away the low idle Working Set the README publishes for a guarantee that only holds until another process asks for its own pages.
- **The limit is a soft bound under concurrency, and the stress test says so**: admission reads the accounted bytes and the message is charged when it is stored, so producers racing on one reading can each store a message that reading said would fit; the first to charge raises the limited flag and the rest are refused, which bounds the overshoot by one message per producer. `a_backlog_driven_to_the_limit_counts_every_message` drives eight producers 2000 sends past a 4 MB limit and holds the broker to that bound, to `accepted + refused == attempts`, to counters that match the refusals of each kind, and to an accounting that equals what is stored and returns to zero once the backlog is drained. On a four-core runner the overshoot does not appear at all: the backlog stops at the 63 messages of 64 KB that fit in 4 MB. *Alternatives considered*: reserving the bytes at admission with a compare-and-swap and handing the reservation to the message's ticket, which makes the limit exact at the price of a loop on the hot path and a second accounting path for every way a message can fail to be stored after it is admitted; refusing a message once the used bytes come within one message of the limit, which trades a known small overshoot for an unknown small shortfall.
- **The stress tests run inside `cargo test --release`**: 3000 connections open, log in, send and die on one loopback listener, half of them holding a message they never acknowledge, and a consumer with a 1000-message prefetch sits on its whole window while another drains 1500 messages behind it. Both finish in under a second, so they guard the broker on every push and on all three platforms CI builds. *Alternatives considered*: the Java acceptance harness, which speaks the real driver but needs a running broker and a Maven build, so it would guard this only when somebody remembers to run it; a long soak with thousands of live concurrent connections, which is what `scripts/soak-compare.ps1` is for and belongs on the machine that publishes the figures.

Still to be designed in 0.5.0: the recovery-action values and options, and the launchd integration.

## Risks / Trade-offs

- [A default memory limit changes behaviour for users with very large backlogs] → Documented; `max_memory_mb = 0` keeps the current unlimited behaviour, the startup log names the limit and where it came from, and the CHANGELOG entry calls the change out.
- [Reading the physical memory is platform code that a Linux container cannot compile for Windows] → The reading is one call per system behind its own gate (`GlobalMemoryStatusEx`, `sysctl hw.memsize`, `/proc/meminfo`), and the arithmetic that turns it into a limit is cross-platform and tested.
